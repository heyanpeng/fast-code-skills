# Fast Commit

## 目标

在用户明确要求提交时，快速识别“本次任务”的实际改动，排除工作区中的无关内容，生成合规的 commit message，完成必要的精准验证并创建 commit。

## 识别本次改动

优先复用同一对话前序 fast skill 的任务上下文中的目标、修改文件和验证结果。没有可复用上下文时，采用两阶段识别，先只获取文件名，再读取候选文件内容：

第一阶段：

- `git status --short`；
- `git diff --name-only`；
- `git diff --cached --name-only`；
- `git ls-files --others --exclude-standard`。

第二阶段：仅对候选文件读取：

- `git diff -- <候选文件>`；
- `git diff --cached -- <候选文件>`。

结合当前对话目标、当前任务中实际修改过的文件、diff 内容、关联测试和项目规范判断归属。

只将能确认属于本次任务的文件或 hunks 纳入 commit：

- 已暂存但与本次任务无关的改动必须排除；
- 未暂存但明确属于本次任务的改动可以选择性加入暂存区；
- 本次任务新建且相关的 untracked 文件可以加入；
- 无法判断归属时停止并列出候选文件，不猜测提交。

不要使用 `git add -A`、`git add .` 或其他会无差别纳入整个工作区的命令。

普通整文件改动使用精确路径 `git add <files>`；只有同一文件混合了本次任务和其他任务改动、且能够可靠拆分时，才做 hunk 级暂存。

## 混合文件处理

如果同一文件同时包含本次任务和其他任务的改动：

1. 优先按 hunks 精确暂存本次改动；
2. 只有能可靠拆分时才继续提交；
3. 无法可靠拆分时停止，说明文件和冲突范围，让用户手动整理。

不得覆盖、回滚、stash、reset 或清理用户的无关改动。

## Commit message

1. 优先读取当前项目的 `AGENTS.md`、提交规范和最近 commit 风格。
2. 根据实际 diff 生成结果导向的 subject。
3. 遵循用户明确指定的提交格式和语言，其次遵循项目规范与近期提交风格。没有约定时，使用 `<type>: <说明>`，说明语言与当前沟通语言一致。以下为中文约定下的示例：

```text
fix: 修复顶部菜单收起逻辑
feat: 支持按容器宽度显示操作菜单
test: 增加 review 修复回归测试
```

4. 一行 subject 足够时不要强行添加 body；多个独立问题或验证边界需要记录时，增加 1～3 条与 subject 语言一致的 body。
5. 用户明确要求“提交 commit”时，直接使用生成的 message 执行提交；用户只要求生成 message 时，不执行提交。

## 提交前检查

提交前执行：

1. 确认最终 staged diff 只包含本次任务；
2. `git diff --cached --check`；
3. 根据本次改动路径运行精准测试、定向 lint/typecheck；
4. 不默认运行全量测试、完整构建或打包。

如果前序任务上下文中的验证结果仍然适用于最终 staged diff，不重复运行；只有 staged diff 发生影响覆盖范围的变化、验证失效或风险升级时才补跑。

如果精准验证失败，默认停止提交并报告失败原因。只有用户明确要求即使失败也提交时才可继续，并在报告中标明失败。

如果 `git add`、`git commit` 或相关 Git 操作因沙箱、权限、`.git/index.lock` 或其他执行环境限制无法完成：

1. 停止继续重试或绕过限制；
2. 保留当前工作区现场；
3. 根据已确认的文件和提交信息，输出可直接复制执行的手动命令，至少包含精确路径的 `git add`、`git diff --cached --check` 和 `git commit -m`；
4. 明确说明 commit 尚未创建，避免声称提交成功。

命令示例：

```bash
git add path/to/changed-file.ts
git diff --cached --check
git commit -m "<符合用户或项目约定的提交信息>"
```

## 安全边界

- 仅在当前分支为 `master` 时，默认停止并要求用户确认；在其他分支（包括 `main`、`release` 或项目明确的保护分支）按用户已明确的提交要求直接提交，不额外确认；
- 不执行 `git commit --amend`；
- 不 push、不创建 PR、不关闭外部 review；
- 不使用 `--no-verify` 绕过 hook；
- 遇到 merge/rebase 冲突时停止；
- hook 如果修改或生成了工作区文件，停止自动继续提交，报告新增改动，让用户确认；
- 不执行 `git reset`、`git clean`、覆盖式 checkout 或其他破坏性操作。

## 提交后报告

提交成功后报告：

```text
Commit：<hash> <subject>
识别为本次任务的文件：<列表>
排除的无关改动：<列表；没有则写无>
自动加入暂存区的文件：<列表；没有则写无>
验证：<实际执行的检查>
未包含：<仍存在但未提交的改动>
```

如果没有可确认属于本次任务的改动，报告原因，不创建空提交。提交失败时保留现场，说明失败原因，不绕过 hook 或自动回滚。

报告中同时列出：识别出的文件、排除的文件、自动暂存的文件，以及仍未提交的文件，便于后续任务继续复用上下文。

## 速度约束

除非风险确实需要或用户明确要求，不默认执行：

- 全量测试；
- 完整构建或打包；
- worktree 创建；
- push、PR 或远程操作；
- 自动修复 hook 问题；
- 其他高开销 workflow。

多个互相独立的精准检查尽量并行执行。

## 沟通约定

- 沟通语言遵循用户明确偏好和项目规范；代码、命令、路径和标识符保持原样；
- 提交前简短说明识别出的文件和 commit message；
- 不把“提交成功”表述为“所有测试通过”，除非确实运行了完整测试；
- 发现归属不确定、保护分支或验证阻塞时立即停止并说明。

## 典型触发示例

- “把这次小需求的改动提交一下，未暂存的本次改动也要包含。”
- “智能识别当前任务改动并提交，不要带上其他文件。”
- “生成 commit message，但先不要提交。”
