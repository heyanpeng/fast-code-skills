# Fast Small Review

## 目标

在小需求完成后快速判断是否存在会阻塞交付的实际问题。聚焦需求符合度、明显回归和验证证据，不把一次小改动扩展成冗长的全量 code review。

## 适用边界

适用于一个明确页面、组件或模块内的低风险改动，例如 UI、交互、文案、配置和简单 Bug 修复。

以下情况应升级到完整审查流程，并明确告知用户。宿主已安装 `code-review` / `review` 等适用技能时可使用；未安装时，使用宿主现有审查能力继续，并按实际风险确定范围和验证，不要求额外安装技能，也不继续声称是快速审查：

- 修改多个独立模块或进行架构重构；
- 修改公共 API、共享组件、协议、数据结构或构建配置；
- 涉及安全、权限、持久化、并发、迁移或跨服务行为；
- 用户明确要求全面审查；
- 精准验证失败，且无法证明与本次改动无关。

## 审查范围

1. 如果用户明确指定 `staged`、`unstaged`、commit、文件或基准点，直接锁定该范围，不再寻找默认分支。
2. 优先消费同一对话前序 fast skill 输出的任务上下文；其中的目标、修改文件和已运行验证可直接作为审查入口。
3. 没有上下文时，优先检查当前工作区未提交 diff；如果没有，再寻找当前分支相对默认分支的 diff。
4. 如果仍无法确定审查范围，报告“没有可审查改动”，不要擅自审查整个仓库。
5. 只读取当前改动路径相关的 `AGENTS.md`、项目规范、调用方、类型和直接相关测试，不做无边界的全仓库浏览。
6. 保留用户已有改动，不执行会覆盖或重置工作区的命令。

## 审查重点

只报告能定位到具体文件和行号、并且具有实际影响的 findings：

- 需求是否真正完成，是否遗漏用户明确要求；
- 是否引入明显的功能回归、状态错误或边界问题；
- 错误处理、空值、权限和禁用状态是否合理；
- 相关测试是否缺失、失效或验证了错误行为；
- 改动是否超出需求范围，是否存在不必要的副作用。

默认不报告：

- 纯个人风格偏好；
- 不影响行为的格式或命名意见；
- 没有证据支持的猜测；
- 可以但不必要的重构建议；
- 与本次改动无关的历史问题。

## 严重级别

- `P0`：阻塞发布、数据损坏或严重安全问题；
- `P1`：高概率功能错误或重要回归，应在交付前修复；
- `P2`：一般功能问题或明显测试缺口，建议修复；
- `P3`：低风险、非阻塞的改进建议。

不要为了凑数量输出 findings。没有可行动问题时，明确写“未发现可行动问题”。

## 默认工作流

1. 用一句话说明审查范围和基准点。
2. 查看 diff 和必要的局部上下文。
3. 运行 `git diff --check`。
4. 根据改动路径运行精准测试、定向 lint 或 typecheck；优先使用测试框架的 `-t` 或等价筛选。
5. 只有发现高影响风险、公共接口变化或精准验证不足时，才扩大验证范围。
6. 不修改代码、不创建 commit、不推送、不创建 PR。发现问题时只提供建议；用户明确要求修复时，再切换到开发流程。
7. 多个互相独立的精准检查尽量并行运行。
8. 如果 diff 没有变化，且任务上下文中的验证仍然适用，不重复运行已通过的验证；只有 finding 需要新证据时才补充精准检查。

## 验证失败处理

区分以下两类情况：

- **本次改动相关失败**：作为 finding 或阻塞项报告，并说明证据；
- **已有、环境或与改动无关的失败**：不算本次 finding，但在验证部分列出。

不要因为测试失败就自动扩大到全量测试，也不要把无法证明的失败归因给本次改动。

## 输出格式

先给结论，再给 findings：

```text
结论：未发现可行动问题。/发现 N 个问题。

Findings：
- [P1] 文件:行号
  问题：具体描述
  影响：为什么会影响功能或交付
  建议：可执行的修复方向

验证：
- 已运行：精准测试、lint/typecheck、git diff --check
- 未运行：列出未运行项目及原因

范围：审查了哪些文件、diff 或基准点。
```

对于明确且适合行级定位的问题，宿主支持时可额外生成行级评论（例如 Codex 的 `::code-comment{...}`）；未提供此能力时，使用包含文件和行号的普通文本。没有明确行级问题时不要生成评论。普通汇总仍需保留。

## 速度约束

除非用户明确要求或风险确实需要，不默认执行：

- 全量测试；
- 完整构建或打包；
- worktree 创建；
- 启动应用、截图或完整视觉回归；
- 子代理拆分；
- 其他高开销 review workflow。

## 沟通约定

- 沟通语言遵循用户明确偏好和项目规范；代码、命令、路径和标识符保持原样；
- 审查发现的问题只报告，不擅自修复；
- 不把“没有发现问题”表述为“代码绝对正确”；
- 若升级到完整 review，说明触发升级的具体原因。

## 任务上下文复用

审查结果中输出并保留：目标、审查文件/基准点、相关但未修改文件、已运行验证、已知失败和 findings。后续 `fast-review-fix` 或 `fast-commit` 应直接消费这些信息，不重新扫描同一范围。

## 典型触发示例

- “快速 review 一下刚才隐藏按钮的改动，不要跑全量测试。”
- “帮我看这个小需求有没有明显回归，只报告问题，不要改代码。”
- “检查当前 diff 是否完成需求，跑相关精准测试即可。”
