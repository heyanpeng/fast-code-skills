# Fast L3 AI Native Pro

## 目标与边界

把需求从仓库探索推进到已验证、可交付或明确阻塞的状态。这个 skill 比普通 L3 流程多一个不可跳过的需求确认阶段：在探索报告完成后，必须逐个问题向用户确认；用户说“可以了”之前，不得创建或修改 `spec.md`、`plan.md`，不得写生产代码、测试代码或其他实现文件。

普通小改动、纯问答、代码解释和不涉及仓库变更的请求不自动套用本流程。需求范围以用户请求为准，不因流程自行扩大到无关重构、依赖升级、生产数据操作或发布。

## 强制状态机

状态只能按以下顺序推进，不得跳阶段：

```text
exploration
  -> interrogation
  -> confirmed
  -> spec_written
  -> plan_written
  -> red
  -> green
  -> refactor_verified
  -> delivery
  -> completed / blocked
```

- `exploration`：只读探索和报告；禁止提问、写代码、写 `spec.md`、写 `plan.md`。
- `interrogation`：一次只问一个问题；等待用户回答后再问下一个；仍禁止写文件。
- `confirmed`：用户明确说“可以了”后进入；不能把普通回答、沉默或“待定”当作完成确认。
- `spec_written`、`plan_written`：按确认内容创建或更新文档。
- `red`：先把验收标准转换成测试函数并运行，确认目标行为缺失导致失败。
- `green`：按计划实现，每一步验证并更新 `plan.md`。
- `delivery`：执行本地门禁、commit、用户授权的 push、CI、合并或发布。

如果用户说“待定”，原样记录该内容，继续下一个问题，不替用户补全答案。如果用户尚未说“可以了”，即使已有足够信息，也只能继续盘问或等待确认。

## 阶段一：探索（禁止提问和修改）

开始后先读取仓库根目录及目标目录最近的 `AGENTS.md`、项目规范、package 配置、测试配置、CI 配置和当前 `git status`。只读检查相关代码、类型、接口、路由、数据结构、测试和已有变更；保留用户已有改动。

探索报告必须回答以下三件事：

1. 需求涉及的能力现在有没有，已经做到哪一步？
2. 相关数据结构、接口、校验规则和权限边界定义在哪里？
3. 有没有半成品，即看起来做了但实际没有闭环的地方？

报告规则：

- 每条结论后面都跟 `文件:行号`；多个证据分开列出。
- 找不到就写“找不到”，不得用猜测补齐。
- 明确区分“已有能力”“部分完成”“未找到”“阻塞”。
- 不提出实现方案，不创建 `spec.md` 或 `plan.md`，不修改任何文件。

探索报告结束后，进入 `interrogation`，不要在同一轮自行开始实现。

## 阶段二：盘问（一次一个问题）

只询问仓库中无法确认、且回答错误会导致返工的问题。仓库已经能确定的内容不得询问。按返工风险从高到低排序，优先询问：

1. 用户可观察结果和验收优先级；
2. 业务规则、权限和数据副作用；
3. 失败恢复、兼容性和边界行为；
4. 交付范围、环境、账号和外部依赖；
5. 非关键实现偏好。

每次只问一个问题，并使用以下格式：

```text
问题 N：<一个可回答的问题>
推荐答案：<建议选择>
理由：<为什么这个答案能减少返工或符合仓库证据>
```

等待用户回答后才能继续。若用户回答“待定”，记录：

```text
待确认：<用户原话>
```

之后继续问下一个问题。不得把推荐答案当作用户确认，也不得把“好的”“继续”解释为“可以了”，除非用户明确说“可以了”或同义的完成确认。

用户说“可以了”后，输出已确认项、待确认原话、关键假设和授权范围，然后进入文档阶段。此前不得写任何项目文件。

## 阶段三：创建 `spec.md`

读取探索证据和盘问结果，创建或更新目标项目中的 `spec.md`。如果项目已有 `spec.md`，先保留有效内容，再修正与本次确认冲突的部分。`spec.md` 至少包含：

```markdown
# 需求目标

# 现状与复用

# 验收标准
## 应该发生什么
- 每条必须可判定对错，并包含验证方式。

## 绝对不能发生什么
- 覆盖权限、失败副作用、数据一致性、安全边界和禁止回归。

# 失败时怎么办

# 这次不做什么

# 假设与限制

# 待确认
- 原样列出用户说过“待定”的内容；没有则写“无”。不得代填。

# 人工验收清单
- `passed` / `not_run` / `not_evaluated` / `blocked`
```

每一条“应该发生什么”至少对应一个正向测试，每一条“绝对不能发生什么”至少对应一个反向测试。不能用“体验良好”“性能正常”这类无法判定的句子作为唯一验收标准。

## 阶段四：创建 `plan.md`

读取 `AGENTS.md` 和 `spec.md` 后创建或更新 `plan.md`。计划的第一步必须是把 `spec.md` 的每一条验收标准转换成测试函数，并标明测试层级：`unit`、`integration` 或 `e2e`。测试函数名必须具体到文件或测试套件，不得只写“补测试”。

计划至少包含：

```markdown
# 验收标准到测试映射
- AC-1：`path/to/test.ts::testName`（unit/integration/e2e）

# 执行顺序
1. 测试先行和 Red 证据
2. 最小实现和逐步 Green
3. Refactor 与回归验证
4. 本地门禁和交付

# 每一步的验证命令

# 复用能力
- 已有模块、接口、fixture、测试账号和 CI job

# 环境、账号、数据和依赖服务

# 完成条件

# 风险、回滚和停止条件

# 执行记录
- 每完成一步标记 `完成`，写上命令、退出码和证据。
```

计划必须说明：实现顺序、每一步验证、完成条件、运行环境、测试账号、测试数据、模拟或真实依赖服务、风险和回滚方式。能复用的已有能力必须写明路径和用途，不得无理由重写。

## 阶段五：Red → Green → Refactor

读取 `AGENTS.md`、`spec.md` 和 `plan.md` 后按计划连续执行，不等待用户安排下一步。

### Red

先实现计划第一步的所有测试函数并运行一次，确认每条验收标准对应的目标行为因尚未实现而失败。记录命令、退出码和失败原因。不得使用 `skip`、`only`、弱化断言、删除场景、修改期望或特殊输入制造假红。

### Green

按 `plan.md` 顺序做最小实现。每改一小步就运行直接相关测试，并在测试失败时读取完整报错和失败产物，定位原因后自行修复并重跑。单元、集成或 E2E 任一已选测试失败，都不能留给后续阶段。

涉及用户流程、跨模块组合或 UI 核心交互时必须包含 E2E；默认使用确定性的 mock/fixture，不调用真实模型、密钥、生产数据或不可控第三方服务。若环境、登录态、账号或外部服务导致 E2E 无法运行，在 `spec.md`、`plan.md` 和最终报告中标记 `blocked` 或 `not_evaluated`，写清尝试命令、原因和补验计划。

每完成一个计划步骤，立即更新 `plan.md`：标记完成状态，记录实际修改、验证命令、退出码、通过/失败证据和未验证项。

### Refactor

只有相关测试全部通过后才能整理重复代码、命名和结构。重构后重新运行受影响范围的完整验证，并再次按验收标准检查。

## 阶段六：本地门禁与交付

完成实现后按 `spec.md` 逐条报告 `passed`、`failed`、`not_evaluated` 或 `blocked`，并执行与风险匹配的测试、typecheck、lint、build、E2E 和 `git diff --check`。不默认扩大到全量测试，但用户流程和发布配置不能用低层测试替代 E2E 或 CI 门禁。

只有用户明确授权相应动作时，才执行 commit、push、合并、部署或发布。提交只包含本任务相关改动，不改写历史、不 force push、不绕过 hook、CI、审批或分支保护。

如果目标远端是 GitLab，并且用户授权 push 后等待 CI：

1. 记录本次 commit SHA、ref、项目路径和远端地址。
2. 设置只读 `GITLAB_TOKEN`、`GITLAB_BASE_URL` 和 `GITLAB_PROJECT_PATH`，不得写入日志、spec、plan 或报告。
3. 优先复用可用的 `scripts/wait-gitlab-pipeline.mjs`；当前仓库已有版本时使用：

   ```bash
   node skills/fast-l3-ai-native/scripts/wait-gitlab-pipeline.mjs \
     --sha "$COMMIT_SHA" \
     --ref "$BRANCH_NAME"
   ```

4. 只接受同时匹配 `sha` 和 `ref` 的 Pipeline。`success` 才能报告“CI 通过”；`failed`、`blocked`、`not_evaluated` 分别报告失败、阻塞或未验证，并停止依赖 CI 的后续合并/发布。
5. 最终报告包含 Push、commit SHA、ref、Pipeline URL、Pipeline 状态、等待时间、失败 Job、未验证原因和下一步。

自动合并或自动发布必须单独得到用户明确授权，并满足所有 required CI、Review approval、无冲突、环境审批、smoke test 和既有发布规则。任何权限、网络、审批、账号或环境缺失都停止并标记阻塞，不绕过保护规则。

## 停止条件

只有以下情况才暂停：

- 缺少权限、账号、环境、服务或无法安全模拟的外部依赖；
- 需要用户或业务方拍板的规则、验收或发布决定；
- 改动范围明显超出 `spec.md` / `plan.md`；
- 同一个问题连续三轮没有实质进展；
- 需要不可逆外部操作，且用户尚未授权。

遇到停止条件时，报告已尝试的方法、证据、阻塞原因和恢复所需动作，不自行猜测或扩大范围。

## 最终报告

最终报告必须包含：

- 需求目标和实际变更；
- 探索结论与证据路径；
- `spec.md` 验收标准逐条结果；
- Red 失败证据、Green 通过证据和 Refactor 后验证；
- 单元/集成/E2E 命令、退出码和失败产物；
- 本地门禁、CI/Review、Push、Pipeline、合并和发布结果；
- 平台状态、人工验收、风险、回滚和未验证项；
- 最终状态：`已上线`、`待上线`、`部分完成` 或 `阻塞`。

不得把本地测试通过、CI 未查询或人工验收未完成报告为“已上线”。
