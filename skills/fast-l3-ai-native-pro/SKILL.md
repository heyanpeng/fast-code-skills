# Fast L3 AI Native Pro

## 目标与边界

把需求从用户输入推进到已验证、可交付或明确阻塞的状态。调用技能后，如果用户还没有提供具体需求，先请用户用自然语言描述目标、范围和期望结果；如果调用消息已经包含需求，则先复述理解。随后默认使用渐进式执行向导，先询问交付终点，再只询问与该终点相关的参数。向导中的每个问题都要同时提供推荐选项和自由输入入口，用户可以回复编号、文字答案或编号加补充条件。需要完全控制时，用户可以进入高级自定义清单。用户选择范围前，不得开始对应动作；需求和执行范围确认前，不得创建或修改 `spec.md`、`plan.md`，不得写生产代码、测试代码或其他实现文件。

用户明确要求了某些动作时，仍先将动作转换为编号清单，请用户用序号确认，避免遗漏或误解。只有用户选中的动作属于本次授权范围。合并入目标分支、部署生产或正式发布必须作为单独编号，不能从“创建合并请求”或“等待 CI/CD”推断得到。

普通小改动、纯问答、代码解释和不涉及仓库变更的请求不自动套用本流程。需求范围以用户请求为准，不因流程自行扩大到无关重构、依赖升级、生产数据操作或发布。

## 强制状态机

状态只能按以下顺序推进，不得跳阶段；未选择的动作必须跳过并记录为 `not_requested`：

```text
intake -> delivery_goal_selected -> scope_details -> execution_scope_confirmed
execution_scope_confirmed -> exploration? -> clarification? -> confirmed
confirmed
  -> spec_written
  -> plan_written
  -> red
  -> green
  -> refactor_verified
  -> delivery_preflight
  -> committed
  -> pushed
  -> merge_request_opened
  -> ci_running
  -> ci_passed
  -> delivery_completed / blocked
```

- `intake`：收集用户需求。如果调用消息已包含清晰需求，复述目标、范围和交付范围；如果没有，先请用户补充需求。仍禁止修改文件。
- `delivery_goal_selected`：用户选择本次交付终点；仍禁止修改文件。
- `scope_details`：只询问当前交付终点需要的参数，并为每个参数提供推荐编号选项和自由输入入口，例如是否盘问、目标分支、CI 失败处理、部署环境和监控停止条件。
- `execution_scope_confirmed`：复述实际动作集合、未包含动作、参数和停止条件，等待用户确认。未确认前不得执行对应动作。
- `exploration?`：交付终点为 `1`～`5` 时包含只读探索；高级自定义模式由动作 `1` 控制。没有选择探索时记录 `not_requested`，不能假装完成探索。选择后续实现动作但未选择探索时，先提示缺少探索授权并暂停。
- `clarification?`：普通模式由“是否进行需求盘问”参数控制，高级自定义模式由动作 `2` 控制。未选择时不主动盘问，但必须把无法确认的关键事项记录为阻塞或未确认。
- `confirmed`：用户在需求确认选择题中选择 `1` 后进入；不能把普通回答、沉默或“暂不确定”当作完成确认。
- `spec_written`、`plan_written`：按确认内容创建或更新文档。
- `red`：先运行测试基线；目标行为缺失时记录失败，已有行为时记录 `baseline_green`，不制造假红。
- `green`：按计划实现，每一步验证并更新 `plan.md`。
- `delivery_preflight`：检查分支、远端、目标分支、凭据、CLI/API 和交付授权。
- `committed`、`pushed`、`merge_request_opened`、`ci_running`、`ci_passed`：分别记录精确的 commit、push、合并请求和流水线证据。
- `delivery_completed`：本次授权范围内的交付动作全部完成；合并、部署和发布只有在单独授权后才执行。

如果用户说“待定”，原样记录该内容，不替用户补全答案。影响验收、权限、数据一致性、外部副作用或发布范围的待定项会阻塞 `confirmed`；非关键偏好可以作为假设继续，但必须在确认摘要和 `spec.md` 中明确记录。如果用户尚未确认需求、执行范围或关键待定项，即使已有足够信息，也只能继续询问或等待确认。

## 阶段一：探索（禁止提问和修改）

开始后先读取仓库根目录及目标目录最近的 `AGENTS.md`、项目规范、package 配置、测试配置、CI 配置和当前 `git status`。只读检查相关代码、类型、接口、路由、数据结构、测试和已有变更；保留用户已有改动。

探索报告必须回答以下三件事：

1. 需求涉及的能力现在有没有，已经做到哪一步？
2. 相关数据结构、接口、校验规则和权限边界定义在哪里？
3. 有没有半成品，即看起来做了但实际没有闭环的地方？

报告规则：

- 每条结论后面都跟 `文件:行号`；多个证据分开列出。
- 找不到就写“找不到”，不得用猜测补齐。
- 明确区分“已有能力”“部分完成”“未找到”“阻塞”。
- 不提出实现方案，不创建 `spec.md` 或 `plan.md`，不修改任何文件。

探索报告结束后，如果用户选择了盘问则进入 `clarification`，否则直接根据已确认范围继续，不要在同一轮自行扩大动作范围。

## 阶段二：渐进式执行向导

每次调用技能都必须在需求输入或复述之后重新输出第一问，不得要求用户记忆编号或引用上一轮菜单。技能先展示当前问题、推荐选项和自由输入提示：

### 第一步：选择交付终点

```text
你希望这次做到哪一步？回复序号或直接描述你的目标。

0. 按推荐：根据需求和仓库状态选择最小安全交付范围
1. 只分析当前需求：探索仓库并输出结论、风险和建议，不修改文件
2. 只产出需求文档：探索、需求确认、创建或更新 spec.md 和 plan.md，不写生产代码
3. 完成本地开发：完成需求确认、spec/plan、测试、实现和本地验证，不 commit、不 push
4. 提交并发起 MR：完成本地开发，再 commit、push、创建 MR，并等待 CI/CD
5. 全链路交付：完成 MR 和 CI/CD，再监控部署、上线状态和 smoke test
6. 高级自定义：进入完整动作清单，逐项选择
```

规则：

- `1` 只读，不创建或修改项目文件。
- `2` 不写生产代码，不创建 commit，不 push，不创建 MR。
- `3` 不创建 commit，不 push，不创建 MR，不等待远程 CI/CD。
- `4` 包含 commit、push、创建 MR 和等待 CI/CD，但不自动合并、不自动部署、不正式发布。
- `5` 包含部署监控和 smoke test。它不自动合并或正式发布，除非用户在高级自定义或覆盖项中明确授权。
- `6` 才展示完整动作清单。普通模式不要求用户理解底层动作编号。

### 第二步：只询问相关参数

根据第一步选择，按需逐个询问。每次只问一个参数，必须展示推荐选项，同时允许用户输入文字或编号加补充条件；仓库已知的分支、环境和 CI Job 必须转换成选项展示：

```text
是否进行需求盘问？回复编号，或直接说明你的选择。
1. 自动判断
2. 必须盘问
3. 不盘问
4. 暂不确定，发现关键缺口时暂停
```

选择 `4` 或 `5` 时询问目标分支。选项优先使用仓库默认分支、已存在的目标分支和项目配置中的候选分支，例如：

```text
目标分支是什么？回复编号，或直接输入分支名。
1. develop
2. main
3. 使用仓库默认目标分支
4. 其他已检测分支
5. 无法确定，先暂停
```

如果 `4` 对应多个分支，继续展示具体分支编号，同时允许用户直接输入已检测到的分支名。选择 `4` 或 `5` 时还要询问 CI/CD 失败处理；选择 `5` 时询问部署环境和监控停止条件。没有涉及的参数不询问。

CI 失败后的处理方式，回复编号，或直接描述处理方式：

```text
1. 失败后停止并报告
2. 自动修复并重跑，最多 3 次
3. 自动修复并持续重试，直到成功或明确阻塞
```

部署环境，回复编号，或直接输入已检测到的环境名：

```text
1. staging
2. production
3. 使用 CI/CD 配置中的默认环境
4. 未配置部署环境，部署完成前暂停
```

部署监控时长或停止条件，回复编号，或直接描述停止条件：

```text
1. 监控到 smoke test 成功
2. 监控 10 分钟
3. 监控 30 分钟
4. 由 CI/CD 完成后结束
```

用户可以连续回复编号，例如：`1,3,2,1`，也可以回复“选择 2，目标分支 develop，CI 失败最多自动修复 3 次”。技能必须按照当前问题顺序解析答案，不把一个问题的编号误用到另一个问题。文字答案与选项含义一致时直接记录；文字答案与选项冲突或无法判断时，重新展示冲突项并要求选择。

### 第三步：确认执行摘要

参数收集完成后，必须输出：

- 实际会执行的动作；
- 明确不会执行的动作；
- 目标分支、环境、重试次数和监控停止条件；
- 仍需用户选择或补充的关键问题；
- 当前授权范围。

最后使用选择题确认，同时允许输入文字确认：

```text
执行摘要是否确认？回复编号或直接输入“确认执行”。
1. 确认执行
2. 返回修改执行范围
3. 返回修改某个参数
```

选择 `1` 后才进入 `execution_scope_confirmed`。选择 `0` 时，技能必须先展示推荐的交付终点和完整动作集合，再继续展示选择题，不能把推荐当作授权。

### 高级自定义清单

用户选择 `6` 时，输出以下完整清单。序号可以根据仓库能力补充，但不得删除关键交付动作：

```text
请选择本次要执行的动作，回复序号或直接描述动作，例如：1,2,3,4,5,6,7

1. 仓库探索：读取规范、代码、测试、CI 配置和当前 git 状态，并输出带证据的探索报告
2. 需求盘问：针对无法从仓库确认且会导致返工的问题逐个提问
3. 创建或更新 spec.md
4. 创建或更新 plan.md
5. 编写或更新测试，并按 Red -> Green -> Refactor 实现代码
6. 本地验证：运行精准测试、typecheck、lint、build、E2E 和 git diff --check
7. 创建 commit
8. push 当前任务分支
9. 创建合并请求（MR/PR）
10. 等待并检查 CI/CD，直到 required Job 结束
11. CI/CD 失败后自动定位、修复、重新验证并再次 push
12. 监控部署、上线状态和 smoke test，直到成功或明确阻塞
13. 自动合并 MR 到指定目标分支（必须同时指定目标分支）
14. 自动部署或正式发布到指定环境（必须同时指定环境）
15. 只输出分析、计划或方案，不修改仓库

高级自定义中的目标分支、部署环境、监控时长和其他约束，必须继续通过选择题逐项确认。
```

规则：

- `1` 是后续仓库实现工作的默认前置动作。用户未选择 `1` 但选择了 `3`～`14` 时，必须先提示缺少探索授权并暂停，不自行补选。
- `2` 未选择时不主动盘问。若关键业务规则、权限或副作用无法安全推断，标记 `blocked`，不能用假设替代用户决定。
- `3`、`4`、`5`、`6` 按用户选择执行。选择 `5` 时默认要求先有 `3` 和 `4`，除非仓库已有等价文档且用户明确允许复用。
- `7`～`14` 只执行用户明确选择的动作。`13` 和 `14` 必须额外确认目标分支或环境，不能从上下文猜测。
- `15` 与任何修改动作互斥。选择 `15` 时只输出结果，不写文件、不 commit、不 push、不创建 MR。
- 用户可以回复“全部”选择 `1`～`12`，但不会自动包含 `13`、`14`；也可以回复“按推荐”接受基于仓库状态生成的最小安全动作集合。
- `15` 与任何修改动作互斥。选择 `15` 时只输出结果，不写文件、不 commit、不 push、不创建 MR。
- 用户回复序号或文字后，技能必须复述“已选择动作”和“未选择动作”；如果序号有冲突、缺少必要参数或无法安全执行，先指出具体问题并等待修正，不得自行补选。

## 阶段三：需求澄清（可选）

### 提问模式

只询问仓库中无法确认、且回答错误会导致返工的问题。仓库已经能确定的内容不得询问。按返工风险从高到低排序，优先询问：

1. 用户可观察结果和验收优先级；
2. 业务规则、权限和数据副作用；
3. 失败恢复、兼容性和边界行为；
4. 交付范围、环境、账号和外部依赖；
5. 非关键实现偏好。

每轮只问一个核心问题，并必须提供 2～4 个互斥选项和自由输入提示，使用以下格式：

```text
问题 N：<一个选择题，也可以直接输入答案>
1. <选项 A>
2. <选项 B>
3. <选项 C>
4. 暂不确定，记录为待确认并暂停相关动作
推荐答案：<建议选择编号>
理由：<为什么这个答案能减少返工或符合仓库证据>
自由输入：可以直接说明你的选择或补充条件
```

如果业务值无法合理压缩成选择题，必须提供“暂不确定”选项，同时允许用户直接输入业务答案。等待用户回复选项或文字答案后才能继续。若用户选择“暂不确定”，记录：

```text
待确认：<用户原话>
```

之后继续问下一个问题。不得把推荐答案当作用户确认，也不得把任意选项当作需求完成确认。所有关键问题回答完成后，再输出选择题：

```text
需求确认是否完成？
1. 确认需求，继续执行
2. 继续回答问题
3. 暂停并保留当前状态
```

选择 `1` 后进入 `confirmed`。用户可以使用自然语言补充原始需求；技能必须提取其中的可执行约束，并在存在歧义时用下一道选择题确认。

用户确认需求和关键问题后，输出已确认项、已选择动作、未选择动作、待确认原话、关键假设和授权范围，然后进入文档阶段。此前不得写任何项目文件。

## 阶段四：创建 `spec.md`

读取探索证据和盘问结果，按项目已有约定定位文档。如果没有约定，使用当前任务作用域的 `spec.md` 和 `plan.md`，不得把无关任务的同名文档直接覆盖或合并。如果项目已有与当前任务对应的文档，先保留有效内容，再修正与本次确认冲突的部分。`spec.md` 至少包含：

```markdown
# 需求目标

# 现状与复用

# 验收标准
## 应该发生什么
- 每条必须可判定对错，并包含验证方式。

## 绝对不能发生什么
- 覆盖权限、失败副作用、数据一致性、安全边界和禁止回归。

# 失败时怎么办

# 这次不做什么

# 假设与限制

# 待确认
- 原样列出用户说过“待定”的内容；没有则写“无”。不得代填。

# 人工验收清单
- `passed` / `not_run` / `not_evaluated` / `blocked`
```

每一条“应该发生什么”至少对应一个正向测试，每一条“绝对不能发生什么”至少对应一个反向测试。不能用“体验良好”“性能正常”这类无法判定的句子作为唯一验收标准。

## 阶段五：创建 `plan.md`

读取 `AGENTS.md` 和 `spec.md` 后创建或更新 `plan.md`。计划的第一步必须是把 `spec.md` 的每一条验收标准转换成测试函数，并标明测试层级：`unit`、`integration` 或 `e2e`。测试函数名必须具体到文件或测试套件，不得只写“补测试”。

计划至少包含：

```markdown
# 验收标准到测试映射
- AC-1：`path/to/test.ts::testName`（unit/integration/e2e）

# 执行顺序
1. 测试先行和 Red 证据
2. 最小实现和逐步 Green
3. Refactor 与回归验证
4. 本地门禁和交付

# 每一步的验证命令

# 复用能力
- 已有模块、接口、fixture、测试账号和 CI job

# 环境、账号、数据和依赖服务

# 完成条件

# 风险、回滚和停止条件

# 执行记录
- 每完成一步标记 `完成`，写上命令、退出码和证据。
```

计划必须说明：实现顺序、每一步验证、完成条件、运行环境、测试账号、测试数据、模拟或真实依赖服务、风险和回滚方式。能复用的已有能力必须写明路径和用途，不得无理由重写。

## 阶段六：Red → Green → Refactor

读取 `AGENTS.md`、`spec.md` 和 `plan.md` 后按计划连续执行，不等待用户安排下一步。

### Red

先对计划映射的测试做一次基线运行。目标行为缺失时，实现测试并记录因缺失行为产生的 Red 证据；如果基线已经通过，记录 `baseline_green`，不得为了制造失败修改期望；如果改动没有适用的自动化测试层，记录 `red_not_applicable`、原因和补验方式。任何情况下都不得使用 `skip`、`only`、弱化断言、删除场景或特殊输入制造假红。

### Green

按 `plan.md` 顺序做最小实现。每改一小步就运行直接相关测试，并在测试失败时读取完整报错和失败产物，定位原因后自行修复并重跑。单元、集成或 E2E 任一已选测试失败，都不能留给后续阶段。

涉及用户流程、跨模块组合或 UI 核心交互时必须包含 E2E；默认使用确定性的 mock/fixture，不调用真实模型、密钥、生产数据或不可控第三方服务。若环境、登录态、账号或外部服务导致 E2E 无法运行，在 `spec.md`、`plan.md` 和最终报告中标记 `blocked` 或 `not_evaluated`，写清尝试命令、原因和补验计划。

每完成一个计划步骤，立即更新 `plan.md`：标记完成状态，记录实际修改、验证命令、退出码、通过/失败证据和未验证项。

### Refactor

只有相关测试全部通过后才能整理重复代码、命名和结构。重构后重新运行受影响范围的完整验证，并再次按验收标准检查。

## 阶段七：本地门禁与交付

完成实现后按 `spec.md` 逐条报告 `passed`、`failed`、`not_evaluated` 或 `blocked`，并执行与风险匹配的测试、typecheck、lint、build、E2E 和 `git diff --check`。不默认扩大到全量测试，但用户流程和发布配置不能用低层测试替代 E2E 或 CI 门禁。

### 交付授权

用户明确要求完成到提交、push、发起合并请求并等待 CI/CD 成功时，确认阶段结束后自动执行以下动作：

1. 创建只包含本任务改动的 commit。
2. 推送当前任务分支并设置正确的 upstream。
3. 创建合并请求，记录 URL、编号、源分支、目标分支和 commit SHA。
4. 等待与本次 commit 和 ref 精确匹配的 Pipeline。若仓库配置了合并请求 Pipeline、deploy/release Job 或 smoke test，必须继续等待这些结果。
5. 只有所有 required Job、部署 Job 和 smoke test 成功，才能报告交付成功。

合并入目标分支、部署生产或正式发布必须单独明确授权。没有该授权时，合并请求创建和 CI/CD 成功后状态为 `待上线`，不得自动点击合并或触发生产发布。

### `delivery_preflight`

在 commit 前一次性检查并记录：

- 当前分支、目标分支、远端 URL、项目路径和保护分支规则；
- 用户授权范围是否包含 commit、push、创建合并请求和等待 CI/CD；
- 可用的 `glab`、`gh`、仓库脚本或等价 API；
- 当前账号、Token、项目权限和创建合并请求所需的环境变量；
- 本次改动是否混入用户已有改动，以及提交信息格式。

如果当前位于受保护分支，按仓库命名规则创建任务分支后再提交。无法确认远端、目标分支、凭据或项目权限时，先标记 `blocked`，不得把改动直接推到其他分支。

### Commit、Push 和合并请求

提交只包含本任务相关改动，不改写历史、不 force push、不绕过 hook、CI、审批或分支保护。提交完成后记录 commit SHA，并在 push 后确认远端 ref 指向同一 SHA。

创建合并请求时使用仓库已有模板和目标分支规则，正文至少包含需求目标、spec/plan 路径、验收结果、测试命令、风险、回滚方式和未验证项。创建失败时读取完整错误，修复可恢复的参数或认证问题并重试；同一问题连续三轮无进展时停止并标记阻塞。

### CI/CD 追踪

优先使用目标项目已有的等待脚本、`glab`、`gh` 或等价 API。技能被单独安装时，不得假设 `skills/fast-l3-ai-native/scripts/wait-gitlab-pipeline.mjs` 一定存在；使用前先检查路径，缺失时切换到可用 CLI/API，并在报告中记录实际入口。

GitLab 轮询至少需要只读 `GITLAB_TOKEN`、`GITLAB_BASE_URL` 和 `GITLAB_PROJECT_PATH`。Token 不得写入命令、spec、plan、日志或报告。只接受同时匹配 commit SHA 和 ref 的 Pipeline。`success` 才能报告该流水线通过；`failed`、`blocked`、`not_evaluated` 分别报告失败、阻塞或未验证。

CI 失败时读取失败 Job 和产物。由本次改动引入的失败必须回到 Green，修复后重新运行本地门禁并重新推送；基线已有的失败不得归因给本次改动，但如果发布规则要求全绿，则保持阻塞。网络超时、没有匹配流水线或缺少凭据不能报告为成功。

最终交付证据至少包含 Push、commit SHA、ref、合并请求 URL 和编号、Pipeline URL、Pipeline 状态、等待时间、失败 Job、部署结果、smoke test 结果、未验证原因和下一步。

## 停止条件

只有以下情况才暂停：

- 缺少权限、账号、环境、服务或无法安全模拟的外部依赖；
- 需要用户或业务方拍板的规则、验收或发布决定；
- 改动范围明显超出 `spec.md` / `plan.md`；
- 同一个问题连续三轮没有实质进展；
- 需要不可逆外部操作，且用户尚未授权。

遇到停止条件时，报告已尝试的方法、证据、阻塞原因和恢复所需动作，不自行猜测或扩大范围。

## 最终报告

最终报告必须包含：

- 需求目标和实际变更；
- 探索结论与证据路径；
- `spec.md` 验收标准逐条结果；
- Red 失败证据或 `baseline_green` / `red_not_applicable` 说明、Green 通过证据和 Refactor 后验证；
- 单元/集成/E2E 命令、退出码和失败产物；
- 本地门禁、CI/Review、Push、commit SHA、合并请求、Pipeline、部署、smoke test、合并和发布结果；
- 平台状态、人工验收、风险、回滚和未验证项；
- 最终状态：`已上线`、`待上线`、`部分完成` 或 `阻塞`。

状态映射：`delivery_completed` 对应 `待上线` 或 `已上线`；存在未完成验证但可以继续等待时对应 `部分完成`；存在权限、环境、流水线或审批阻塞时对应 `阻塞`。

不得把本地测试通过、CI 未查询或人工验收未完成报告为“已上线”。
