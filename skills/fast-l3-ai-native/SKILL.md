# L3 AI Native 实战

当用户明确要求使用 L3 实战、AI Native L3、L3 开发流程，或要求按学习文档执行需求时，按本技能工作。目标是把需求从提出推进到可发布、已发布或明确阻塞的状态；不能把本地测试通过当作上线完成。普通的小改动、纯问答、代码解释和不涉及仓库变更的请求不自动套用完整流程。对合理且可执行的需求默认持续推进：不因为缺少现成 `spec.md`、`plan.md`、常规实现选择或非关键歧义停下来询问；自动采用最小、可回滚的方案并记录假设。只有真实的业务决策、权限、环境、外部依赖或未获授权的外部变更才暂停。

## 总体原则

- 先读取仓库根目录及目标目录最近的 `AGENTS.md`，再检查当前工作区状态；遵守项目已有规则，不覆盖用户的无关改动。
- 先查现状再决定实现方式：搜索相同用户结果、类型、接口、事件、配置、测试和进行中的变更。明确记录是 `reuse`、`extend`、`replace` 还是 `new`。
- 将不确定性显式写出。优先依据用户请求、仓库约定和最小风险假设继续推进；需要业务决定、权限、外部服务或环境准备且无法安全推断时，记录为阻塞，不发起流程性询问。
- 需求范围以用户请求为准；不得因为 L3 流程自行扩大为依赖升级、跨项目重构、真实服务操作或发布操作。
- 开始前直接整理已有输入：需求目标、目标仓库/环境、上线范围、验收人、可用测试依赖和发布权限。缺少非关键输入时采用保守默认并记录；缺少关键权限或环境时标记为阻塞。

## 执行模式

- `spec.md` 和 `plan.md` 不是用户必须提供的输入。缺少时根据请求和仓库现状创建；已有时复用并修正过期内容。
- 按风险选择验证强度：用户流程、跨模块、权限、数据一致性和发布配置默认走单元/集成/E2E；窄范围样式、文案或配置改动使用与风险匹配的精准验证，但仍覆盖可观察结果。
- 用户明确要求“从分析到上线”、指定部署环境或授权发布时，视为已授权该范围内的 push、合并、部署和 smoke；只要求本地实现或 PR 时，不继续执行未授权的合并和发布。
- 发现仓库已有本地 CI 门禁时，优先执行该入口；没有时根据 CI 配置组合等价命令。远程 CI 通过前不得声称已上线。

## 阶段一：需求探索

开始编码前，先完成仓库探索并向用户报告：

1. 需求涉及的能力现在在哪里，已经做到哪一步。
2. 相关数据结构、接口、校验规则和权限边界定义在哪里。
3. 是否存在半成品、重复实现或可以复用的能力。
4. 正常路径、边界条件、失败恢复和安全约束是什么。

报告必须带文件路径和行号；找不到的内容写“未找到”，不要推定存在。需求明确但细节有歧义时，采用最小范围、可回滚的默认方案，并记录假设、影响和后续验收方式。

## 阶段二：`spec.md` 与 `plan.md`

先根据用户请求和仓库现状创建或更新需求文档，再按文档连续推进实现：

### `spec.md`

至少包含：

- 问题与目标；
- “应该发生什么”，每条都能判定对错；
- “绝对不能发生什么”，覆盖权限、失败副作用、数据一致性和安全边界；
- 失败与恢复；
- 本次不做什么；
- 假设与限制；
- 人工验收清单，并区分已验证、未验证和外部阻塞。

每条正向验收标准至少对应一个正向测试，每条禁止事项至少对应一个反向测试。

### `plan.md`

计划必须先安排测试，再安排实现，并写清：

- 验收标准到单元、集成、E2E 测试函数的映射；
- 复用的模块、接口和夹具；
- 实现顺序及每步验证命令；
- 所需运行环境、测试账号和模拟依赖；
- 完成条件、风险、回滚方式和必须停止的阻塞条件。

完成 `spec.md` 和 `plan.md` 后直接进入生产实现，不等待额外确认；文档中的假设、风险和阻塞状态作为后续验证依据。

## 阶段三：Red → Green → Refactor

按计划连续工作：

1. **Red**：先写或更新本次风险等级适用的目标测试，分别运行并确认因目标行为缺失而失败。涉及用户流程时必须包含 E2E；窄范围样式、文案或配置改动使用相应的精准验证。记录命令、退出码和失败原因；不得用 `skip`、`only`、弱化断言或修改期望制造假红/假绿。
2. **Green**：实现满足契约的最小方案，优先复用已有能力。已选择的单元、集成或 E2E 测试任一失败时，都必须读取报错和失败产物、定位根因、修复实现或测试夹具并重跑；不得把失败留给后续阶段，不得用 `skip`、`only`、放宽断言、删除场景或单个测试输入的特殊分支规避失败。
3. **Refactor**：只有相关测试全部通过后才能整理重复代码和样式；重构后重新运行影响范围内的完整验证。

按风险覆盖以下测试层级：

- 单元：纯函数、状态机、组件分支或服务分支；
- 集成：真实组合的服务、持久化、IPC、sidecar 或文件边界；
- E2E：涉及用户流程、跨模块组合或 UI 核心交互时，从用户入口验证完整可见结果和失败恢复。

涉及用户流程和跨模块流程时，E2E 不得仅用单元或集成测试替代。至少覆盖一条主成功路径，以及本次改动影响的关键边界或失败恢复路径；涉及 UI 时还要覆盖核心交互、可访问名称/角色、关键视口或响应式约束。优先复用仓库现有的 Playwright/Cypress 配置、fixture 和测试账号，使用用户可见文本、可访问性角色或稳定的 `data-testid` 定位，不依赖脆弱的 CSS 结构或坐标。默认 E2E 必须使用确定性的 mock/fixture，不调用真实模型、密钥、线上服务或不可控的第三方系统；需要真实协议验证时单独标记 `@live` 或人工验收。

如果环境、登录态、测试账号或外部依赖导致 E2E 无法运行，必须在 `spec.md`、`plan.md` 和最终报告中标记 `blocked` 或 `not_evaluated`，说明已尝试的命令、具体原因和补验计划；不能用 `skip`、`only`、放宽断言或删除场景掩盖缺口。新增用户流程时，计划必须包含 E2E 用例文件、运行命令、失败产物（截图、trace、视频或 HTML 报告）及 CI Job 映射。

Electron 改动要保持主进程、preload、renderer 边界；跨进程能力同步检查共享类型、preload 白名单、可信 sender 校验和权限/路径校验。涉及外部协议时先确认协议能承载需求，缺字段要在最早校验点明确拒绝。

## 阶段四：本地验证与交付准备

完成后按 `spec.md` 逐条报告：已通过、失败、未验证、外部阻塞，并附命令和证据。至少执行与影响范围匹配的测试、类型检查、构建和差异检查；除非用户明确要求全量测试或 PR/发布流程要求，不主动扩大到全量回归。推送前必须执行仓库已有的本地 CI 门禁；若不存在，则执行与远程 CI 等价的本地命令集合。

涉及用户可见流程时，必须执行对应 E2E 命令并记录退出码；失败时保留并检查 Playwright/Cypress 的截图、trace、视频或 HTML 报告，报告中写明失败步骤和根因。仅在 E2E 不受影响且 `plan.md` 明确说明理由时，才可以不重跑既有 E2E。

跨平台能力要分别检查 macOS、Windows、Linux。当前机器结果不能冒充其他平台通过；缺少 Runner 或环境时标记 `not_evaluated`，记录原因和补验计划。

涉及 UI 时使用可访问性角色、名称或用户可见文本定位，并验证结构、可操作性、溢出、关键断点和核心状态。涉及真实第三方服务时，夹具测试不能代替真实协议验证；需要保留 `@live` 或人工验收证据，但不得在默认 E2E 中调用真实模型、密钥或线上服务。

提交前检查仓库要求的治理校验、格式检查和分支/提交约定。提交信息遵循项目约定；本项目默认使用 `type(scope): 中文说明`。只提交本任务相关改动，不提交无关文件，也不改写已有提交或 force push。

在用户授权的交付范围包含 CI、PR、push 或上线时，本地验证完成后将本任务的提交推送到当前任务分支对应的远端，以触发远端 CI 并继续交付流程。若本任务改动尚未提交，按项目约定创建仅包含本任务改动的提交后再推送。推送前确认远端和目标分支；没有配置上游分支、远端目标不明确、分支受保护或推送失败时，停止并报告具体原因，不得改推其他分支或强制推送。只授权本地实现或 PR 时，不擅自执行后续发布动作。

区分失败归因：

- `introduced_failure`：由本次改动引入或改变，必须修复并重跑。
- `baseline_blocked`：目标基线已有、且本次改动未新增的失败；不扩大范围修复无关问题，但必须在报告中保留证据。若项目发布门禁要求全绿，则状态为阻塞，不能声称 CI 通过。

## 阶段五：PR、CI/CD 与上线

本地绿灯后继续推进交付闭环，不停在“代码写完”：

1. **准备 PR**：检查目标分支、分支命名、提交信息、变更范围、影响映射、测试证据、人工验收清单、风险和回滚方案。涉及 UI、跨平台、IPC、权限、sidecar 或发布配置时，补充对应证据。
2. **运行 CI 门禁**：读取仓库现有 `.gitlab-ci.yml`、GitHub Actions 或等价流水线配置，确认实际运行类型检查、受影响测试、构建、E2E、治理校验和必要的安全检查，并先执行本地等价门禁。E2E Job 必须上传失败截图、trace、视频或 HTML 报告等可审计产物；以目标分支最新代码的临时合并结果和隔离环境 CI 为准，本机结果不能替代 CI。
3. **处理红灯**：读取 CI/Review 日志，按 `introduced_failure` 或 `baseline_blocked` 定位根因。前者必须补测试或修实现后重新运行门禁；后者不修无关历史问题，但在发布门禁要求全绿时停止发布。不能通过删除测试、放宽断言、跳过 Job、`--no-verify` 或改写期望消除红灯；同一问题连续三轮无进展时停止并记录阻塞原因。
4. **人工验收**：按 `spec.md` 逐条核对正常、边界、失败恢复、权限、UI 和平台行为。macOS、Windows、Linux 分别记录 `passed`、`not_run`、`not_evaluated` 或 `blocked`，不能用单个平台结果代替全部平台。
5. **合并与发布**：CI 通过、Review 满足要求且人工验收达到发布条件后，按用户请求的目标范围执行合并、打包、部署或发布。优先使用仓库已有流水线和发布入口，不直接改生产数据或绕过审批；缺少必要权限时记录阻塞并停止。
6. **上线确认**：记录发布版本、源 Commit SHA、目标环境、发布时间、执行入口和回滚方式；运行发布后的 smoke/健康检查，确认用户可见的关键路径。失败时按既定回滚方案处理并保留证据。

如果请求范围只包含本地实现或 PR，则完成该范围并将后续合并、发布标记为待上线，不发起额外询问。

## 完成状态

最终报告必须明确属于以下哪一种：

- `已上线`：代码已合并并发布，发布后检查通过；
- `待上线`：本地和 CI/Review 已通过，但等待合并、发布或人工验收结果；
- `部分完成`：已完成实现或 PR，但仍有测试、平台或外部依赖未验证；
- `阻塞`：缺少权限、环境、业务决策或外部服务，无法安全继续。

报告包含：变更摘要、spec 验收逐条结果、单元/集成/E2E 的 Red/Green 证据（含 E2E 命令、退出码、覆盖场景及报告产物）、CI/Review 结果、平台状态、发布版本与 SHA、上线检查、风险和回滚方式。未运行的命令必须说明原因。

## 停止条件

出现以下情况时停止当前自动流程，记录问题、已尝试方法和阻塞原因：

- 关键业务约束无法从请求、仓库约定或已有文档安全推断；
- 缺少权限、账号、服务或无法安全模拟的外部依赖；
- 改动范围明显超出当前的 spec/plan；
- 同一问题连续三轮没有实质进展；
- 需要执行不可逆外部操作、合并、发布或改变生产数据，且用户未授权该操作。
