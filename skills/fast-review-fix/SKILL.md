# Fast Review Fix

## 目标

把代码审查意见快速闭环：确认问题仍然存在，做最小范围修复，补充必要的回归测试，并逐条提供验证证据。不把一次 review 修复扩展成无关重构或全量开发流程。

## 输入

支持以下 review 问题来源：

- `fast-small-review` 产生的 findings；
- 用户粘贴的 code review 意见或行级评论；
- 已经定位清楚的测试失败或回归问题。

如果没有明确的 finding 或可复现问题，先说明缺少修复目标，不要自行猜测大范围问题。

## 适用边界

适用于一个明确页面、组件或模块内的低风险修复，例如 UI、交互、文案、配置和简单 Bug。

遇到以下情况时，明确告知用户已超出快速修复范围，并停止自动扩大改动：

- 跨多个独立模块的重构；
- 公共 API、共享组件、协议、数据结构或构建配置变更；
- 安全、权限、持久化、并发、迁移或跨服务问题；
- 多个高风险 finding 之间存在未解决的设计冲突；
- 用户明确要求完整重构或全面修复。

## 默认工作流

1. **整理 findings**：优先消费前序 `fast-small-review` 的任务上下文；按 `P0 → P1 → P2 → P3` 排序，同级按依赖关系和风险排序；保留每条 finding 的文件、行号、问题和验收条件。
2. **逐条核实**：读取当前代码和最小必要上下文，确认问题仍然存在。发现 finding 不成立或已被其他改动解决时，不改代码，记录证据。
3. **确认边界**：用户明确目标优先于 review 建议。若 review 建议会改变用户目标或扩大范围，先说明冲突并在必要时追问。
4. **最小修复**：只修改解决 finding 所需的代码；保留用户已有改动；优先使用 `apply_patch`，宿主未提供时使用其等价的局部编辑工具；不执行覆盖或重置工作区的命令。
5. **回归测试**：可复现的行为缺陷优先补最小回归测试；已有测试足够覆盖时复用或增强，不创建无关测试矩阵。
6. **精准验证**：为每条已修复 finding 至少运行一个直接相关的测试或检查，并运行 `git diff --check`。根据改动路径选择精准测试、定向 lint 或 typecheck，不默认跑全量。
7. **轻量复查**：只复查本次修复 diff，确认没有明显副作用、需求偏离或新的回归；不重新执行完整 review。
8. **结果汇报**：逐条标记 `已修复`、`无需修改（不成立/已有实现）` 或 `阻塞（需要用户决策）`，同时列出验证证据和未运行的检查。
9. **更新上下文**：输出目标、修改文件、相关但未修改文件、已运行验证、已知失败和仍未解决的 findings，供 `fast-commit` 直接复用。

## Findings 处理规则

- 不盲目接受 review 意见；先用代码、测试和项目规范核实。
- 不为修复一个 finding 顺手做无关重构、命名清理或风格调整。
- 如果无法复现但风险仍存在，保留 finding，说明证据不足和建议的下一步验证。
- 如果多个 findings 共享同一根因，可以一次最小修改解决，但必须逐条回报覆盖关系。
- 对不成立的 finding 不创建“为了回应 review”而存在的代码。

## 严重级别

- `P0`：阻塞发布、数据损坏或严重安全问题；
- `P1`：高概率功能错误或重要回归；
- `P2`：一般功能问题或明显测试缺口；
- `P3`：低风险、非阻塞改进。

如果发现修复过程中实际风险高于原 finding，立即升级说明，不继续按低风险流程扩展。

## 验证策略

优先使用：

- 受影响测试文件中的 `-t` 或等价精准筛选；
- 新增或复用的最小回归测试；
- 改动文件的定向 lint/typecheck；
- `git diff --check`。

测试失败时区分：

- 与本次修复相关：作为阻塞或未完成项报告；
- 已有、环境或与本次无关：不归因给本次修复，但在验证结果中列出。

不要因为单个测试失败就自动扩大到全量测试，也不要无证据地修改无关代码。

如果多个 findings 可由同一测试命令覆盖，合并为一次验证；不要逐条重复启动测试。轻量复查只检查本次修复 diff，不重新执行完整 review。前序上下文中的验证仅在 diff 变化、覆盖范围失效或风险升级时重跑。

## Git 与外部状态

默认只修改工作区，不自动 `git add`、commit、push、创建 PR 或操作外部 review 评论。只有用户明确要求时才执行这些动作。

## 输出格式

```text
结论：已修复 N 条，需用户决策 M 条，无需修改 K 条。

逐条处理：
- [P1] finding：已修复
  修改：做了什么
  验证：运行了什么
- [P2] finding：无需修改（不成立/已有实现）
  依据：为什么不需要改
- [P1] finding：阻塞（需要用户决策）
  原因：缺少什么信息或存在什么冲突

验证汇总：
- 已运行：精准测试、lint/typecheck、git diff --check
- 未运行：列出项目及原因
```

如果用户提供了行级评论（例如 Codex 的 `::code-comment`），在汇报中保留对应文件和行号，但不要自动关闭或修改外部评论状态。需要时，使用宿主提供的行级评论能力报告新增问题；未提供此能力时，使用包含文件和行号的普通文本。

## 速度约束

除非用户明确要求或风险确实需要，不默认执行：

- 全量测试；
- 完整构建或打包；
- worktree 创建；
- 启动应用、截图或完整视觉回归；
- 子代理拆分；
- 完整 `code-review` / `review` 流程。

## 沟通约定

- 沟通语言遵循用户明确偏好和项目规范；代码、命令、路径和标识符保持原样；
- 开始时说明将处理哪些 findings；
- 遇到关键歧义、权限或范围阻塞时立即说明；
- 不把测试通过表述为“代码绝对正确”；
- 不创建 commit，除非用户明确要求。

## 典型触发示例

- “修复刚才 review 的 P2 测试缺口，只跑相关测试。”
- “按这几条 PR review 意见逐条修复，不要顺手重构。”
- “这个测试失败已经定位了，帮我修掉并补一个回归测试。”
