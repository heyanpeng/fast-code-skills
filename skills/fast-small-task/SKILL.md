# Fast Small Task

## 目标

在不牺牲基本正确性的前提下，快速、完整地交付已有项目中的小需求。优先缩小调查和验证范围，不把小改动升级成全量开发流程。

## 适用边界

将需求视为小需求的启发式条件：

- 影响一个明确页面、组件或模块；
- 不需要数据库迁移、复杂领域模型、跨服务协议或大规模重构；
- 可以通过局部测试、静态检查或明确的手工检查验证。

如果需求涉及多个独立模块、公共协议、构建配置、数据结构或复杂新功能，明确告知用户它已超出本 skill 的快速范围，并切换到更完整的开发流程，不要为了追求速度而强行套用本流程。

## 默认工作流

1. **读取约束**：只读取当前改动路径相关的 `AGENTS.md`、项目规范和测试约定；保留用户已有的未提交改动。
2. **快速定位**：使用 `rg`、`rg --files` 和少量上下文读取定位入口、调用方和直接相关测试，不做无目的全仓库浏览。
3. **确认假设**：能从代码和上下文确定的内容直接执行；只有会改变实现方向、影响范围或安全性的歧义才追问。开始修改前，用一句话说明范围和关键假设。
4. **最小修改**：只修改完成需求所必需的文件和逻辑，优先复用现有模式；优先使用 `apply_patch`，宿主未提供时使用其等价的局部编辑工具。
5. **精准验证**：
   - 优先运行受影响测试文件中的相关用例，使用 Vitest/Jest 的 `-t` 或等价筛选；
   - 对直接相关的组件行为、类型或 lint 做最小检查；
   - 始终运行 `git diff --check`；
   - 测试不存在、启动成本过高或本身不稳定时，采用最小可行验证，并明确说明未运行的检查。
6. **按风险升级**：只有修改公共组件、共享工具、路由、协议、跨页面状态、构建配置、依赖或数据结构，或精准测试失败且可能由本次改动引起时，才扩大测试或构建范围。
7. **结果汇报**：简要说明完成内容、保留的行为、实际运行的验证、未运行的验证及已知风险。

## 任务上下文复用

完成时输出并保留以下上下文，供同一对话后续的 `fast-small-review`、`fast-review-fix` 或 `fast-commit` 直接复用：

- 目标：用户需求和验收条件；
- 修改文件：实际改动的路径；
- 相关但未修改文件：用于理解范围的路径；
- 已运行验证：命令、筛选范围和结果；
- 已知失败：与本次改动相关或无关的失败；
- 未解决假设/findings：需要后续确认的事项。

如果同一对话已有前一个 fast skill 的任务上下文，直接复用其范围、文件和验证结果；除非 diff 变化、验证已失效或风险升级，否则不重复读取规范、扫描模块或重跑已通过验证。

## 验证选择矩阵

按实际改动选择最小验证，不默认执行全量测试：

- 文案/CSS/JSON：`git diff --check`，必要时补格式检查；
- TS/TSX：受影响测试文件的 `-t` 精准测试，加变更文件定向 lint；
- 只改测试：只运行相关测试；
- 公共组件、路由或配置：精准测试加 typecheck，只有证据显示风险扩大时才升级；
- 多个互相独立的检查尽量并行执行。

## 速度约束

除非用户明确要求，或任务风险确实需要，不默认执行：

- 全量测试；
- 完整构建或打包；
- worktree 创建；
- 启动应用、截图或完整视觉回归；
- 长篇实施计划；
- 其他高开销 workflow skill。

多个互相独立的精准检查应尽量并行执行，而不是串行等待。

## UI 改动规则

按钮、布局、样式等低风险 UI 改动默认以代码和精准测试验证为主。只有在布局风险明显、用户提供视觉参考或用户明确要求时，才启动应用进行视觉检查。

## Git 规则

默认不创建 commit、不推送、不创建 PR。只有用户明确要求时才执行，并遵守项目中的 commit 格式和分支规范。

## 用户沟通

- 沟通语言遵循用户明确偏好和项目规范；代码、命令、路径和标识符保持原样；
- 开始时只做一次简短范围说明；
- 遇到阻塞、需要授权或关键歧义时立即说明；
- 完成时不要声称“全部通过”，除非确实运行并通过了对应范围的验证；
- 对与本次改动无关的已有测试失败，单独标注，不擅自修复。

## 典型触发示例

- “隐藏桌面端 PPT 编辑页顶部分享按钮，保留更多菜单里的入口，只跑相关测试。”
- “把这个页面的提示文案改掉，不要跑全量测试。”
- “修复这个单页按钮点击后状态不更新的问题，完成后做精准验证。”
